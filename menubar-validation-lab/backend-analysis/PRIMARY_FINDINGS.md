## 2. 多 spacer 的确定性容量边界

核验源：MenubarHide a4476bfe81a9a84ac94f8dfb273c4eaad8f9e960 的 CollapsedGeometry.swift。[G1]

其几何函数采用以下规则。单位都是 NSScreen 等来源的逻辑点，不是显示器硬件像素：

status_width 指该屏幕的状态区域：有刘海时为右侧辅助区域，无刘海时按此源模型采用全宽。不能将随前台应用菜单长度变化的剩余空白当成 status_width；否则 width 与 status_width 的大小关系会错误触发“刘海”分支。

- 非刘海模型阈值为屏幕宽度的一半。
- 刘海模型阈值为右侧状态区域宽度的 0.75 倍。
- 取全部屏幕中的最小阈值 c_min。
- 单个占位宽度 u = max(200, floor(c_min - 64))。
- 所需 spacer 数 = max(ceil(最大状态区域宽度 / u) - 1, 0)。
- 实际 spacer 数最多 6 个，另有一个 separator，所以最大总占位是 7u。

“0.75”“64”“六个”是此实现的选择，其中阈值建立在上游作者记录的有限观察上，不是 Apple 的稳定接口承诺。

### 本轮可复现的数值

以下含人为构造的边界样本，不应当写成已连接这些显示器。

| 输入的逻辑几何 | 单项宽度 | 所需 / 实际 spacer | 最大总占位 | 对模型覆盖目标的不足 |
|---|---:|---:|---:|---:|
| 1512 pt 刘海屏，状态区 663.5 pt | 433 | 1 / 1 | 3031 | 0 |
| 上述屏幕 + 2560 pt 外屏 | 433 | 5 / 5 | 3031 | 0 |
| 上述屏幕 + 3024 pt 外屏 | 433 | 6 / 6 | 3031 | 0 |
| 上述屏幕 + 3031.5 pt 人工边界 | 433 | 7 / 6 | 3031 | 0.5 pt |
| 上述屏幕 + 3440 pt 外屏 | 433 | 7 / 6 | 3031 | 409 pt |
| 上述屏幕 + 3840 pt 外屏 | 433 | 8 / 6 | 3031 | 809 pt |
| 上述屏幕 + 5120 pt 外屏 | 433 | 11 / 6 | 3031 | 2089 pt |

这里的“不足”严格指代码意图中的“separator + spacers 覆盖最宽状态区”没有达到。实际系统还会受到已有项目宽度、系统溢出策略和屏幕布局的影响。因此，不能直接把 809 pt 的模型差额解释成“macOS 实际必然漏出 809 pt 的图标”。

对全部非刘海屏的组合，上限约为 7 × floor(最窄屏宽 / 2 - 64)，并非无条件等于最窄屏的 3.5 倍。存在刘海时，约束来自状态区，不能只比较屏幕全宽。[G1][G2]

### 最小宽度会覆盖掉安全余量

u 的下限是 200。因此，极窄的人工几何可以产生两个不同问题：

- 模型阈值是 225 时，u = 200，实际余量只有 25，不再是计划中的 64。
- 模型阈值是 195 时，u = 200，单项宽度已经达到或越过模型阈值。

这证明有限域上的计算矛盾，不证明这些人工几何一定由真实 Mac 暴露。运行器应在读取到异常或不足的几何时拒绝收起，不继续尝试大宽度。

## 3. 本项目的 guarded_candidate 与上游不是同一测试对象

本目录的 Python 计算器保留源公式，但在外层增加输入和可行性检查：

- 屏幕列表为空、非有限数、非正宽度、状态区大于屏幕宽度时拒绝。
- 总容量不足时拒绝。
- 单项达到模型阈值或未保留 64 pt 余量时拒绝。
- 即使通过，也只允许进入人工 Mac 实验，不能直接通过产品验收。

如果本轮 Controller 采用同样的保护，它应标为 guarded_candidate，并在记录中包含 derived_from 提交与行为差异。不能将这个原型的结果标成“上游完整版本通过”，也不能直接用它对比上游性能。

该原型可以验证“让左侧项目进入系统溢出”的候选行为，不会因此自然获得搜索、自动排序、三分区或动态镜像。

尤其“普通隐藏”和“始终隐藏”有不同语义：普通展开时，后者是否仍保持收起？搜索是否能找到它？专用展开是否能访问？本轮几何函数并没有证明这些语义。应单列为尚未实施或待测，不能仅凭所有图标进入同一个 overflow 菜单就判断三分区完整等价，也不能反推原生 overflow 路线永远无法实现三分区。

## 4. 私有允许列表：为什么本轮仅探测

核验源：Hidden Bar ee3af2475431540ddfa211b9e1e64b08a156f8f0 的 shim 和 NativeVisibilityEngine。[H1][H2]

shim 明确动态加载 MenuBarClientCore.framework，通过 MBAssessmentModeConfiguration / MBAssessmentModeAssertion 建立允许列表。第三方应用按 bundle 允许，系统项另有整数列表；不能把两者统称为逐 Item 管理。

进一步核验到的限制：

1. 上游使用系统项 0..<64，并明确说这是在 27.0 检查过的范围。符号可加载和数组可传入，不证明所有当前系统项目都已包含。
2. 上游检查应用位于 /Applications 之下。源码注释说从构建目录、Downloads 或某些其他路径运行时，即使允许 bundle，图标也可能隐藏；~/Applications 也未被其保护函数当成合格位置。
3. 源码记录该路径会影响时钟/通知中心，需要临时解除限制和专用交互处理。
4. 源码记录摄像头／麦克风使用者名称提示可能被隐藏，角点仍保留。默认补救只在新的采集开始时展开一次，并不阻止用户随后再次隐藏。
5. 上游已有 generation 检查：旧激活请求晚成功时立即 invalidate，避免覆盖新的展开意图。这说明异步生命周期不能用一个 active 布尔值代替。

以上是代码及作者记录，不是我们在 Mac 上复现的结果。

因此，本轮 Controller 只做只读探测，不发出 activateWithConfiguration。私有显隐 A/B 保持 not_run，不能用“探测到类存在”来代替“隐藏成功且无副作用”。这是一条有明确范围的实施决定，不是推定用户不愿意使用私有接口。

若之后进入受控激活实验，最小前提应包括：Mac 实际编译运行、独立于菜单栏箭头的退出入口、人工开始、有限时长、到期与晚回调释放、自己和已知项目的保留策略、切屏/退出/权限变化取消，以及对系统状态逐项观察。相同进程里的定时器不能保证主线程卡死时照常运行；清理方法存在也不能证明崩溃后系统一定恢复。不能用“有超时”替代恢复实测。

## 5. 同一套任务的比较原则

实际 A/B 应固定系统 build、目标 App 版本与路径、屏幕逻辑尺寸、缩放、菜单栏设置及权限状态。先运行无管理器基线，再测试每条明确命名的候选；在候选之间撤销本工具的临时改动。

观察目标应包括：

- 同 App 多 Item 的身份是否串掉；同 Item 多屏副本是否误算成两个目标。
- 动态数值是否新鲜，静态图标是否丢失测试所需信息。
- 左键、右键、Option 和菜单内动作分别是否落在正确目标。
- 菜单未结束时，规则和收起请求是否打断交互。
- 刘海、外屏、缩放和全屏变化后，保存意图是否可解释。
- 时钟、通知中心、摄像头/麦克风系统提示是否保持正常。
- 用户自己重排后，旧任务是否覆盖新布局。
- 普通展开、始终隐藏、专用展开是否有明确的区别。
- 拒绝权限、项目退出、晚回调和失联时，结果是否诚实标记未知或不支持。

本目录不会替运行者生成这些实机结果；缺少这些证据时，后端状态仍是未验证。

## 7. Controller 的只读交叉审查

本节检查本轮工作副本的 `Controller/Sources/Geometry.swift` 与 `Controller/Sources/main.swift`。这是源码审查，不是 Swift 编译或 macOS 运行记录。本环境没有 Swift 编译器、AppKit 或可用 Mac；可执行证据仍限于第 6 节的 Python 几何验证。

### 候选计算器与固定上游的差异

Controller 保留了上游的 0.75 刘海系数、64 pt 预留量、200 pt 最小单项宽度和最多 6 个辅助 spacer，以及由所有屏幕最小阈值约束单项宽度、由最大状态区决定需求的公式。[G1] 它增加了以下行为，因此标记 `guarded_candidate` 是准确的：

- 上游空列表返回 200 pt 单项宽度、0 个辅助 spacer；Controller 拒绝没有屏幕的输入。
- Controller 拒绝非有限数、非正宽度和状态区超过屏幕全宽的输入；固定上游几何函数没有这些成组输入检查。
- Controller 在转为 Int 前将 spacer 需求裁至 6，避免极端输入的整数转换问题；上游先转 Int，再裁剪数量。
- Controller 显式检查结果是否有限、单项是否达到候选阈值、实际余量是否至少为 64 pt、总跨度是否覆盖模型需求。上游仅计算并返回受限数量，没有对应的“拒绝实验”结果。
- Controller 将通过状态命名为 `model_allows_experiment_not_verified`，并写出固定来源和仅为几何模型的证据等级；它没有把公式通过当成隐藏成功。

Controller 用 `Double` 表达输入，固定源使用 `CGFloat`。本轮未执行 Swift 版本，也没有据此声称跨语言或所有边界逐位等价。Controller 从 `NSScreen` 的全宽、safe area 和刘海右侧区域构造输入；缺少右侧区域数据时拒绝猜测。屏幕 API 的实际返回和几何策略的运行行为都仍需 Mac 验证。

对于 1512 / 663.5 pt 刘海屏加 3440 pt 非刘海屏，模型得到阈值 497.625 pt、单项 433 pt、实际余量 64.625 pt、6 个辅助 spacer、总跨度 3031 pt、模型差额 409 pt。Controller 的结果应为 `allowed: false`、`candidate_capacity_shortfall`，并在新的收起宽度赋值前退出。`collapse()` 在几何判定前会请求撤销之前的实验，因此“拒绝新收起”不等于“没有发生任何布局调用”。更不能把这个拒绝写成 macOS 实际漏出了图标或候选后端已经通过恢复测试。

### 审查中发现并已修正的两处问题

第一处是理由与布尔值可能矛盾。早期工作副本分别用 `unit >= cliff` 形成拒绝理由、用 `unit <= cliff - 64` 计算允许值。人工输入全宽和状态区均为 1e20 时，在二进制浮点中 `cliff - 64` 可以舍入回 `cliff`，使拒绝理由与允许值并存。该例仅用于检查数值边界，不代表真实屏幕尺寸。最终源码计算 `headroom = cliff - unit`，依次检查阈值、实际余量和容量，再由唯一的成功理由派生 `allowed`。已只读核验这项修正存在；没有将 Python 中的浮点复现写成 Swift 实机测试。

第二处是拒绝操作的顺序。早期工作副本先调用 `restore(reason: "replace_experiment")`，再检查鼠标按钮，可能在宣称拒绝新布局变化前已经改变本应用的占位长度。最终源码把 `NSEvent.pressedMouseButtons` 检查移至 `collapse()` 开头，位于恢复和长度写入之前。这只能保护该入口的新收起请求，不等价于完整的菜单会话锁。

### 尚未覆盖的运行边界

现有实验的到期恢复仍可能在用户交互期间执行；界面已明确说明这一点，并标示菜单会话锁、真正的规则引擎和三分区尚未实现。5 秒延迟是可重复注入触发的实验工具。10 秒定时器只是主运行循环里的恢复请求，不能证明主线程阻塞、崩溃或系统异常时一定按时恢复。

恢复函数只重置本应用 spacer 的长度和标题，并不写回其他应用的排序；这减少了主动覆盖他人排序的范围，但没有证明系统自身重排或用户拖动后完全无干扰。定位标记仍需人工放置并记录基线。右键、Option、同应用多项目、系统状态提示和菜单持续打开的行为都必须依照共同协议观察，不能由上述源码保护替代。

本次交叉审查确认的是候选计算器会诚实拒绝已知模型条件不满足的输入，以及两处源码问题已修正。没有产出任何新的 macOS 兼容性、显示正确性或恢复成功结论。
