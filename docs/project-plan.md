# 调酒师开源版｜项目计划书 v0.2

制定日期：2026-11-20  
计划性质：产品研发与 Agent 协作的首版执行基线。  
当前状态：方案与启动材料已编制；远端仓库、执行主机和模型调用尚未接入，产品任务尚未派发。本版已按外部交叉审查核对原始 JSON/Python 并修订；完整关闭记录见 [审查修订记录](audit-v0.2.md)。

## 1. 项目目标与完成定义

本项目开发一款官方免费发行、自有代码采用 MIT 许可证的 macOS 菜单栏管理工具。第一版帮助用户整理低频项目，同时保持正确项目可达、原菜单可用、动态状态可信、正在进行的输入与用户新布局得到保护。

开发以版本化任务与交付物推进。一次对话结束、模型返回成功或执行进程退出，都不构成产品完成。代码任务完成需要可追踪的 Git 提交、独立检查、合并记录与验收结论；实验任务完成需要完整可复查的证据，其研究结论允许为失败。

本轮增加一套 Agent 开发小组工作方式：多个角色按明确模块边界并行工作，使用独立工作区，经过统一集成队列合并。产品技术方案不因采用 Agent 开发而降低正确性要求。

## 3. 两条交付轨道

### 3.1 产品轨道

延续 M0—M5：

- M0：真实 Mac 构建、无管理器基线、端口契约与验证夹具。
- M1：正确身份、刘海／溢出条件下的原项访问、恢复与系统完整性。
- M2：把已验证的路线接入最小产品流程。
- M3：权限、多屏、会话、用户修改、睡眠与退出恢复，并由 APP-26 独立汇总裁决。
- M4：APP-25 完成可访问性和本地化实现，APP-22 独立验收，再进行签名公证、更新与支持说明。
- M5：小范围试用，作出正式 v1 或继续技术预览的决定。

M1 是关键路径。macOS 26 的 AX／临时槽位与 27 原生 overflow 可以分别研究；不要求两种系统同时成功才能评价一条明确范围内的路线。组合使用多个访问能力时，必须对组合路线跑完整用户任务。

实验研究被 accepted 仅说明研究交付完整。产品路线只有经独立审查得到 verified，才满足 M1 产品门槛。所有失败的研究也应被接受和保存，不能因没有正面结论而无限重跑。

### 3.2 协作轨道

协作基础采用从薄到厚的方式：

| 阶段 | 交付内容 | 不作为前置的内容 |
|---|---|---|
| 启动方式 A | 任务卡、角色提示、独立 Git 工作区、人工协调登记、一个可用 CLI、串行 PR 集成 | 完整远端控制台、两个执行器同时接好 |
| 薄自动化 B | 结构化任务输入／结果、执行收据、资源租约、预算与取消、只读协调板 | 通用 Agent IDE、插件市场、多租户平台 |
| 稳定运行 C | 持久协调账本、断连对账、自动检验与合并队列、第二执行器 | 无限制递归子 Agent、跨主机共享文件式调度 |

启动方式 A 就可以开始产品 M0。OPS-05 / OPS-06 中一条实际执行路线通过即可验收 OPS-07；自动调度仅在 automation_runtime_ready 打开后启用。人工 bootstrap 可先使用已授权 CLI 与同一收据格式，不形成等待自身调度器的循环。尚未实现的适配器不进入调度候选。

## 4. 人与 Agent 的责任

用户是项目负责人，决定产品范围、资源投入和公开发行。已确认的任务范围内，Agent 自主实现、修复、检查和提交；不为每个可逆步骤重复请求确认。

协调服务是执行规则的程序，管理状态、资源和收据；协调 Agent 负责拆任务、提出优先级与处理需要判断的异常。两者不是同一个权限主体。

| 角色 | 职责 | 模型候选 | 输出 |
|---|---|---|---|
| lead | 范围、优先级、阻塞收敛与分工建议 | gpt6.2astra | 任务契约与决策记录 |
| architect | 产品端口、数据模型、跨模块契约 | gpt6.2astra | ADR、接口与影响分析 |
| core | 身份、状态机、协调与持久化纯逻辑 | gpt6.2sol | 模块提交与针对性检查 |
| platform | AppKit、AX、几何与系统能力适配 | gpt6.2sol | 平台代码与实际能力证据 |
| ui | 目录、设置、焦点、无障碍与本地化实现 | gpt6.2sol | 原生界面与交互结果 |
| validation | 真实 Mac 基线、行为复现与独立验收 | gpt6.1terra | 原始记录、缺陷与验收结论 |
| reviewer | 独立反例审查与证据裁决 | grok4.7 → gpt6.2astra | ReviewVerdict 与 GateDecision |
| integrator | 工作区、CLI 适配器、工程清单、CI、候选与发行准备 | gpt6.2sol | 可复现环境及 IntegrationReceipt |

这是初始岗位分配，不是经过本项目基准证明的模型排名。OpenAI 官方对 Astra／Sol／Terra 的一般定位，以及 Grok 4.7 的公开能力，可以作为起点；具体选择仍要比较实际补丁质量、返工、时延和用量。[C1][X1]

同一模型可以承担多个角色，但同一任务的作者与独立审查者必须是不同 run；作者的子 Agent 不充当唯一独立审阅人。角色数量不等于同时运行的会话数量。

## 5. 并行策略与资源

初始上限是项目策略建议，接入后可以根据额度与任务调整：

- 全局最多 4 个活动模型会话，协调、评审和子 Agent 均计入。
- 同时最多 3 个实现写入任务；当评审积压时优先保留审查容量。
- 每个真实 Mac GUI 主机同时最多 1 个任务；确认旧任务停止并恢复基线后才能交接。
- 子 Agent 初始深度最多 1 层，每个任务最多 2 个，受全局容量和父任务预算约束。
- 签名和正式发行使用单独的受控作业，不与普通写代码的 shell 共用凭据。

资源按 linux_cpu、macos_build、macos_gui_exclusive 分类。linux_cpu 是可用的首选资源，不强制任务只能在 Linux 执行；纯 Swift 能否在该环境验证取决于已安装工具链和模块依赖。AppKit 构建与原生行为必须使用对应 Mac 资源。

实现资源与验收资源按阶段取得；all_of 表示各类检查都要完成，不表示从编码开始一直同时占用所有资源。APP-17/18 的实现资源已统一为 macos_build，GUI 只在交互和集成观察时申请。编码与验收可以要求不同资源。例如在远端写目录逻辑后，需要 Mac 编译；本工具真实焦点／快捷键的验证还要取得 GUI 租约。任务卡分别表达实现环境与验证环境，不能因代码在 Linux 写成，就记录 Mac 验收通过。

Mac GUI 租约按整台主机排他。性能和时序敏感测试期间暂停同机高负载构建。两台物理或独立隔离的 Mac 可以分开排队，但不能凭两个 worktree 认为获得两套菜单栏。

## 6. 执行波次与关键路径

`phase` 表示归属工作包；OPS 的 W0 是协作基础工作包，产品使用 M0—M5。`wave` 才表示推荐启动波次；同波仍受依赖、门槛与资源约束。以下表格直接从 tasks.json 生成，覆盖全部 34 张卡，包含 OPS-06/07。

| 启动波次 | 任务（仍须逐项满足依赖） | 工作目标 |
|---|---|---|
| W0 | OPS-01, OPS-02, OPS-03, OPS-04, OPS-08, APP-01 | 章程、工作区、共享构建布局与协调底座；波次内仍遵守依赖。 |
| W1 | OPS-05, APP-02, APP-03, APP-04, APP-05, APP-06, APP-07, APP-08, APP-09, APP-11 | 基线、身份和候选路线；首个执行器与可独立开发的纯模块。 |
| W2 | OPS-06, OPS-07, APP-10, APP-12, APP-13, APP-14, APP-15, APP-16, APP-17 | 垂直流程；第二执行器可选推进，调度服务在已有执行器上验收。 |
| W3 | APP-18, APP-19, APP-20, APP-21, APP-26 | 可靠性验收与 APP-26 汇总裁决。 |
| W4 | APP-22, APP-23, APP-25 | APP-25 界面补齐 → APP-22 独立验收 → APP-23 候选产物。 |
| W5 | APP-24 | 真实试用后决定正式版或继续预览。 |

关键路径是：Mac 基线 → 身份观察 → 至少一条真实访问路线 → 独立 M1 裁决 → 适配器接入 → 完整流程 → 可靠性 → 候选包。

APP-25 或后续修复改变相关发行候选时，生成新的 APP-26 attempt：重跑受影响 M3 验证，或附独立签署的未受影响证据复用依据，再签发当前 candidate/scope/context 绑定；W3 历史裁决不直接放行 W4 产物。

没有 Mac 或没有合格访问路线时，可以继续完成纯模型、配置与接口工作，但不扩大界面和增强功能来掩盖关键路径阻塞。M1 每完成一轮实验就复盘；没有新假设时不通过重复调用模型制造进展。

## 7. 时间、成本与进度管理

当前不承诺确定日期：真实主机、额度与后端可行性尚未验证。采用滚动计划，每次只承诺下一波具备前置条件的任务。

首批代表任务包括身份探测、纯状态机、原生焦点与一次审查。记录：

- 从 ready 到 accepted 的耗时，分开计算排队、执行、审核和修复。
- 每个 accepted 任务的模型与工具用量；订阅额度和 API 金额分开，不能混算。
- 首次审查通过比例、返工次数、集成冲突次数。
- Mac GUI 等待时间、实验中断与恢复成本。
- 产品任务成功率、错误目标数、布局被覆盖次数和手动修理次数。

未知成本显示 unknown，不填 0。子 Agent 和重试都计入父任务与全局预算。初始启动包中的金额和 token 上限留为待配置，不会因为文档生成而自动发起付费调用。

使用“已接受任务数”观察工程流动，但产品发布仍看 F01—F12 的实际能力矩阵。不能用 90% 任务卡完成来掩盖唯一剩下的刘海不可达问题。

## 8. 项目完成与发布要求

代码任务 accepted 应同时具备：

1. 任务契约和来源版本明确；
2. 改动路径在授权范围内，必要接口变更经过协调；
3. 作者提交与独立审查绑定精确版本；
4. 所需检查在正确环境执行，原始证据能追溯；
5. 最新基线上的集成候选已验证；
6. 实际合并结果已确认；合并后的产物仍对应验证树；
7. 未解决限制已进入支持矩阵，不以“基本完成”掩盖阻断。

研究任务可以用完整的负面结论完成，不强制进入生产路径。单任务 accepted、某候选 verified、产品 M1/M3 gate 与最终发布决定分别存储。

正式 v1 仍要求：主要目标刘海场景存在真实访问路径；没有错误目标、自动打断、系统状态损害或覆盖用户修改；权限降级、退出恢复、配置迁移、签名与更新在实际产物上成立。

## 10. 计划变更规则

产品范围变更写 ADR；接口改变先更新契约再派依赖任务；运行资源变化更新 registry。每次变更记录原因、影响任务、是否使旧审查失效及需要补做的验证。

主 Agent 的聊天摘要可以帮助导航，正式事实以版本化契约、任务卡、运行收据、Git 与验收证据为准。新会话从这些材料恢复，不依赖记得上一段对话。

## 11. 本版固定的工程与验收底座

根 Package.swift 负责当前 Packages/... 与 Tests/... 的 Swift target 图，App 外壳用固定版本 XcodeGen 从 project.yml 生成工程。新增已定义模块下的源文件尽量不改共享工程清单；新增 target、依赖和构建配置仍经集成者串行处理。生成 pbxproj 不作为手工维护权威。OPS-03 定义工作区和生成规则，APP-01 定义模块契约；精确工具版本与实际 Mac 工程生成/构建由 APP-13 验证后登记，见 [构建布局 ADR](adr/build-layout.md)。

| M0_BASELINE_VERIFIED | ALL(APP-02 accepted; evidence:selected_mac_baseline_verified) | APP-02 | APP-03, APP-12, APP-13 |

Python 工具负责离线检查、文档生成与门槛语义参考；未来 TypeScript/Node.js/SQLite 服务负责运行账本和派工。两者共用 JSON 契约与回归样例，Python 工具没有 live state 写入权。完整接口见 [机读契约说明](../contracts/README.md) 与 [门槛判定说明](gate-evaluation.md)。

本包已纳入 B1/B2、它们引用的研究报告及历史 Lab 源树；来源与迁移后的 SHA-256 见 [基线来源清单](baselines/provenance.json)。本轮没有改变任何历史实验结论。

项目计划、架构说明、任务书、协调板及依赖视图均可由 python3 tools/render_docs.py 生成；--check 用于检测漂移。任务数据中的状态仍为规划状态，离线回归通过不等于工程任务 accepted。
